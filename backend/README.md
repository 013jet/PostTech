# JanaМен · Backend

Fastify 5, TypeScript, PostgreSQL, драйвер `pg`. Node.js 24.x, pnpm 11.25.0.

Будущие подключения: [схема архитектуры](../docs/architecture.html) и [описание 1С:ЗУП / Documentolog](../docs/INTEGRATIONS.md). Это проект интеграций; runtime-адаптеры, outbox/inbox и webhook ещё не реализованы.

## Запуск

```powershell
pnpm install --frozen-lockfile
pnpm dev:local
```

Для Windows x64 поставляется локальная сборка PostgreSQL через dev-зависимость `embedded-postgres` (суффикс beta относится к упаковщику). Она запускает процесс PostgreSQL, а не имитацию базы. В `pnpm-workspace.yaml` разрешены только установочные скрипты бинарного пакета Windows и esbuild.

Первый запуск создаёт `backend/.local/database.json` со случайным паролем и кластер `backend/.local/postgres/`. База: `127.0.0.1:55432`, API: `127.0.0.1:3001`. Повторный запуск применяет отсутствующие миграции и добавляет отсутствующие аккаунты, сохраняя записи и пароли.

Локальные аккаунты имеют пароль `JanaLocal2026!`: `employee@janamen.local`, `manager@janamen.local`, `hr@janamen.local` (HR-администратор). Дополнительно есть `timur@janamen.local` (член команды) и `outside@janamen.local` (другой сотрудник). Все записи вымышлены.

Для уже установленного PostgreSQL скопировать `.env.example` в `.env`, задать `DATABASE_URL`, затем:

```powershell
pnpm db:migrate
pnpm db:seed
pnpm dev
```

`db:seed` создаёт локальные тестовые аккаунты. Для внешней базы его запускают только по осознанному выбору разработчика. `dev` и `start` сами seed не выполняют. `pnpm build` собирает TypeScript, `pnpm start` запускает сборку с подготовленной БД.

API слушает только loopback. Фронт обращается через прокси Vite `/api`. `ALLOWED_ORIGINS` задаёт точный список разрешённых адресов интерфейса.

Если API не может запуститься (например, порт занят или `PORT` некорректен), Fastify закрывается вместе с пулом PostgreSQL. Исходная ошибка запуска сохраняется; служебные подключения не остаются открытыми. Обычное завершение сервера также закрывает пул.

## Сессии и доступ

- Пароли хешируются `scrypt` с индивидуальной солью. В БД хранится хеш случайного токена сессии. Cookie: `HttpOnly`, `SameSite=Strict`, путь `/api`, срок 12 часов. `Secure=false` используется для локального HTTP. Токен не хранится в localStorage и не возвращается в JSON.
- Вход ограничен десятью попытками в минуту на IP. Выход удаляет сессию и cookie; истёкшая сессия возвращает 401.
- Для изменений обязателен `X-Janamen-Request: 1`; проверяются Host и Origin. API не разрешает cross-origin credentialed-запросы.
- Пользователь и роль определяются по сессии. Сотрудник получает свои заявки и профиль; руководитель — заявки прямых подчинённых. Клиент не задаёт автора, роль, номер, статус, длительность, списание или историю.
- Миграция `003_hr_role.sql` добавляет роль `hr`, сохраняя существующие записи. HR получает каталог и заявки своей компании по полю `company`, включая историю; это кабинет просмотра, без права подачи, отзыва или согласования отпуска за сотрудника. Полноценного управления кадрами пока нет.
- Сотрудник получает только собственный объект `employees`; имя руководителя уже есть в нём. Руководитель получает себя и прямых подчинённых, без дат приёма подчинённых. HR получает рабочие кадровые поля компании. Ответы формируются явным списком полей: дополнительные JSON-поля автоматически не публикуются. Только собственный профиль, личные контакты и уведомления доступны всем трём ролям. Обучение доступно только назначенному сотруднику.
- SQL-параметры передаются отдельно от текста запросов. В журналы и ошибки не записываются пароли, cookie, тела запросов или строки подключения.

## API первой версии

Все пути начинаются с `/api`. Тело — JSON. Ошибка: `{ "code": "…", "message": "…" }`.

| Метод и путь | Тело / результат |
|---|---|
| `GET /health` | Проверка API и PostgreSQL |
| `POST /auth/login` | `{ email, password }`; устанавливает cookie |
| `POST /auth/logout` | `{}`; отзывает сессию |
| `GET /workspace` | `{ session, today, employees, profiles, requests, notifications, courses, enrollments }`, только доступные записи |
| `POST /requests` | `{ startDate, endDate, comment, sourceRequestId? }`; возвращает `{ id }` |
| `POST /requests/:id/decision` | `{ decision: "approved" или "rejected", comment }` |
| `POST /requests/:id/withdraw` | `{}` |
| `POST /notifications/:id/read` | `{}`; только своё уведомление |
| `POST /notifications/read-all` | `{}`; только свои уведомления |
| `PATCH /profile/contacts` | `{ email, phone }`; только свои контакты |
| `POST /courses/:id/lessons/:lessonId/complete` | `{}`; отметка своего назначенного материала |
| `PATCH /courses/:id/answers` | `{ questionId, optionId, revision }`; сохранение ответа |
| `POST /courses/:id/quiz/submit` | `{ revision }` и `Idempotency-Key`; серверная оценка, возвращает `{ id }` попытки |
| `POST /courses/:id/quiz/retry` | `{ revision }`; новая попытка после неуспешной сдачи |

Для `POST /requests` обязателен `Idempotency-Key` в формате UUID. Повтор того же содержимого с тем же ключом возвращает тот же номер без новых истории и уведомлений. Использование ключа для другого содержимого даёт 409. Фронт сохраняет ключ при повторе после потери ответа. Номера уникальны, но могут иметь пропуски после отменённых транзакций или перезапуска PostgreSQL.

`today` — дата Казахстана. Даты отпуска — ISO `YYYY-MM-DD`, оба конца периода включены. `createdAt` — дата создания в Казахстане, время истории — ISO UTC, отображаемое в UTC+5. `Employee.vacationDays` в снимке — исходный остаток; фронт вычисляет доступный, вычитая `deductedVacationDays` из заявок. Сервер независимо считает остаток по `vacation_debits`.

Ответы: 400 — неправильные поля/даты/комментарий; 401 — нет сессии; 403 — нет прав или запрещён источник; 404 — запись не найдена; 409 — конфликт статуса, дат, остатка или ключа; 429 — слишком много попыток.

## Правила и сохранение

- Переходы: `pending → approved | rejected | cancelled`. Повторное решение и согласование после отзыва запрещены.
- Повторная подача доступна для своей отклонённой/отозванной заявки. Создаётся новая запись со ссылкой на источник; источник не меняется.
- При создании и одобрении проверяются остаток и пересечение с одобренным отпуском того же сотрудника. Ожидающие заявки не резервируют дни. Отклонение остаётся доступным.
- Изменения блокируют строку сотрудника через `SELECT … FOR UPDATE`. Параллельные решения по разным заявкам проверяют последовательно обновлённые данные.
- Одобрение, списание, история и уведомление сохраняются одной транзакцией. Первичный ключ списания — номер заявки: повторное списание невозможно. Отказ и отзыв дни не расходуют.
- Снимок кабинета читается согласованно в read-only транзакции Repeatable Read.

`pnpm test` требует работающий PostgreSQL; использует `DATABASE_URL` либо локальный конфиг. Тесты создают случайную схему `test_*`, выполняют настоящие SQL-операции и удаляют только свою схему. Рабочие заявки не сбрасываются.

`migrations/` — SQL-схема; `src/local.ts` — локальный PostgreSQL и запуск; `src/server.ts` — API с подготовленной БД; `src/app.ts` — маршруты и сессии; `src/workflow.ts` — транзакции заявок; `src/academy.ts` — обучение; `src/security.ts` — пароли, токены, даты; `test/` — интеграционные сценарии, включая параллельные решения и тесты.

## Academy

Миграция `002_academy.sql` добавляет курсы, назначения, попытки и ссылки уведомлений на курсы. Материалы и приватные ключи тестов хранятся в PostgreSQL; `seed-data/academy.json` — исходные учебные примеры для локального seed. Их больше нет в исходниках фронта. Перезапуск не перезаписывает материалы, назначения или результаты.

- Айдане и Тимуру назначены два курса с начальным прогрессом 0. Старое браузерное сохранение не импортируется. Курсы пока являются учебными примерами, не официальными материалами компании.
- Сотрудник видит только свои назначения. Руководитель и неназначенный сотрудник не получают чужих курсов, ответов или результатов.
- `courses[].quiz.questions` содержит только вопросы и варианты, без `correctOptionId` и `explanation`. Приватные ключи используются при серверной проверке и возвращаются только в разборе уже отправленной попытки (`attempts[].review`).
- Курсы, материалы, вопросы, варианты ответов и сохранённый разбор попыток возвращаются по явному списку полей. Дополнительные служебные поля в JSON базы не публикуются, в том числе в старых результатах тестов.
- Отметки материалов идемпотентны. Материалы обязательны до сохранения ответов и сдачи теста; сервер проверяет существование вопроса и варианта. Клиент не передаёт оценку, факт прохождения или дату завершения.
- Сохранение ответа, сдача и пересдача требуют актуальную `enrollment.revision`. При изменениях из другого окна API возвращает `409 STALE_PROGRESS`, фронт загружает свежие данные. Это предотвращает перезапись более новых ответов.
- Сдача блокирует строку назначения. Попытка, серверная оценка, завершение и уведомление записываются одной транзакцией. Один ключ отправки даёт одну попытку; параллельные разные ключи не создают вторую попытку в завершённом состоянии.
- Проходной балл — 80%. Неуспешный результат сохраняется, новая попытка очищает текущие ответы и сохраняет историю и материалы. Успешное прохождение даёт 100% прогресса и одно уведомление с переходом к результату. После завершения ответы и результат не изменяются.

Тесты `test/academy.test.ts` проверяют права, отсутствие приватных ключей до сдачи, обязательность материалов, черновики, устаревшие изменения, серверные оценки 0% и 80%, пересдачу, конкурирующие запросы, уведомления и сохранение при повторном запуске приложения и seed.

Тесты `test/server.test.ts` используют временные порты: проверяют очистку пула при неудачном запуске, реальный HTTP-запрос к `/api/health` и освобождение подключений при завершении. Работающий локальный API на порту 3001 они не останавливают.

AI, почта, SSO, восстановление пароля, управление сотрудниками и производственный деплой в этот этап не входят. Учётки, курсы и исходные остатки пока создаёт локальный seed.
